1. 目的と概要

DBに保存済みのレシートデータから「モンスターカード」を自動生成し、2人のプレイヤーがそれぞれ1枚のカードを選んで対戦するゲームを、既存のレシート解析システムに追加する。着想は「バーコードバトラー」で、レシートの店舗・商品・金額・購入日時などでモンスターの強さと姿が決まる。

デモ画面を開く

  • 2人対戦（別々のPC）。相手が一定時間参加しなければコンピュータ（P2）と対戦する。
  • プレイヤーは管理者ログイン不要。席は「ルームを作った人＝P1、コードで参加した人＝P2」。
  • カードとイラストはSVGで生成する。勝敗はサーバーで計算する（不正防止）。
  • 既存のレシート解析・保存・削除の機能は変更しない。

2. 前提・用語

用語意味
有効なカード保存済みレシートから作られ、対戦で使えるカード（状態 ACTIVE）。下書き・未解析は含まない。
表示レシートカード選択画面に並ぶレシート。有効なカードの元レシートから選ぶ。カードは「選ぶ」まで伏せる。
手札プレイヤーが「このレシートを選ぶ」で呼び出したカード。最大3枚。
画像カード「レシート画像から作る」で作ったカード。1体のみ。手札の3枚には数えない。
席／ルームルームは6桁コードで識別。席トークンを持つ2人（P1・P2）だけが操作できる。
前提：レシートの解析の行テキストは画面に表示しない。表示するのは構造化データ（店名・日時・商品・金額など）だけ。画像、テーブル名、画像ハッシュも出さない。

3. 全体の流れ

  1. ロビー（作成／参加）
  2. 待機（コード共有・90秒）
  3. カード選択
  4. 対戦（自動再生）
  5. 結果（元レシート公開）
  1. P1がルームを作り、6桁コードをP2に伝える。P2はコードで参加する。
  2. 待機から既定90秒（設定で変更可）でP2が参加しなければ、コンピュータがP2になる。
  3. 両者がカードを1枚決定すると、サーバーが勝敗を計算し、ログを再生する。
  4. 結果画面で、選ばれた2枚の元レシートを両プレイヤーに公開する。「同じルームで再戦」で3へ戻る。

5. カード生成アルゴリズム

入力はレシートの構造化データと画像のSHA-256（デモは疑似ハッシュ）。画像ハッシュの先頭32ビットを乱数の種にし、同じ入力から同じカードを作る（アルゴリズム版数 2）。

5.1 属性

商品カテゴリ別に金額を合計し、最大のカテゴリで決める。飲食＝炎、食料品＝土、日用品＝風、交通・移動＝雷、それ以外／商品なし＝無。

5.2 要素（すべて0〜1）

記号内容計算
A合計金額min(合計, 30000) / 30000
M最高額の商品min(最高額, 10000) / 10000
C文字数min(文字数, 600) / 600
N商品数min(商品数, 20) / 20
T時刻帯（未設定は12時）min(12, |時 − 12|) / 12
W日付(日−1)/30 × 0.7 ＋ 週末なら0.3
r(k)ゆらぎ種を5ビットずつずらして8ビット取り出した値 / 255

5.3 ステータス

項目式
HP200 + floor(500 × (0.25A + 0.30C + 0.15N + 0.15W + 0.15r0))
ATK40 + floor(100 × (0.25M + 0.25C + 0.15T + 0.15W + 0.20r1))
DEF30 + floor(80 × (0.15A + 0.30N + 0.20C + 0.15W + 0.20r2))
SPD40 + floor(60 × (0.35T + 0.20W + 0.15C + 0.10N + 0.20r3))
LUCK5 + floor(20 × (0.50r4 + 0.25W + 0.25C))
必殺技倍率round((1.5 + 0.5 × (0.2M + 0.4C + 0.4r5)) × 100) / 100

金額（A・M）が各ステータスに与える影響は25%以下に抑え、カードの数値から金額帯を言い当てにくくする。

条件補正

×1.10 は floor(値 × 11 / 10)。

5.5 総合力・レア度・名前・イラスト

  • POWER ＝ floor(HP/5 + ATK + DEF + SPD/2 + LUCK×2)。
  • レア度：POWER 345以上＝SSR、315以上＝SR、275以上＝R、未満＝N（目安はN25%・R40%・SR25%・SSR10%）。
  • 必殺技名は属性ごとの3種から、名前は属性ごとの接頭辞4種と接尾辞6種から、種で決める。
  • イラストは属性別の体形に、目・角・牙・ほほ紅などを種で変えたSVG。生成AIのSVGが検証を通らない場合の代替表示として使う。SVGは <img> のデータURIで表示し、スクリプトを実行させない。

6. 対戦・勝敗判定アルゴリズム

  • 1〜20ラウンド。各ラウンドで、先攻→後攻の順に1回ずつ行動する。
  • 先攻はSPDが高い側。同値は battleSeed の偶奇で決める。
  • 行動3回目ごとに必殺技（倍率＝必殺技倍率）、それ以外は通常攻撃（倍率1）。
  • ダメージ ＝ max(1, round(max(1, ATK×倍率 − DEF×0.5) × (0.9〜1.1の乱数) × 属性倍率 × 会心倍率))。
  • 属性相性：炎→風→土→雷→炎 の順に有利（1.25倍）、逆は不利（0.8倍）、それ以外・無属性は1倍。
  • 会心：確率 LUCK%、1.5倍。
  • HPが0になった側が負け（KO）。20ラウンドで決着しなければ、残りHP割合 → POWER の順で判定し、同じなら引き分け。
  • 乱数は battleSeed（サーバーが生成）から作る。同じ battleSeed と同じ2枚のカードなら、必ず同じ結果になる。

7. カード選択の仕様

7.1 画面の構成

  1. タブ「レシートを選ぶ」「レシート画像から作る」。
  2. 「レシートを選ぶ」：表示レシート（最大9枚・3×3）、「シャッフル」（10件以上のときのみ）、手札（0〜3枚）、選択中カードと「このカードで決定」。
  3. 「レシート画像から作る」：ファイル選択／ドロップ欄、状態メッセージ、作ったカード1体のプレビュー。生成回数や3枚の制限の表示は出さない。

7.2 状態と無効化

状態シャッフル各レシートの選択タブ・画像生成
手札0枚有効（10件以上のとき表示）有効有効
手札1〜2枚無効有効有効
手札3枚無効無効（選択済み以外も）無効
決定後無効無効無効

画像カードは手札に数えないため、手札が0〜2枚の間は、何度でも作り直せる。

7.3 表示レシートの内容

レシートの形をした面に、MR-18の項目をすべて表示する。見せる相手は、そのレシートを配られた本人だけ（対戦開始前）。カードは「選ぶ」まで見せない。

7.4 選び方の規則

  • 9枚は、有効なカードから、相手に配った分と手札のカードを除いてランダムに選ぶ。
  • 相手に1枚、自分に最大9枚。有効なカードが2枚未満のときは対戦できない（ロビーへ戻す）。
  • 再戦のたびに配り直し、手札・画像カード・選択をリセットする。

8. コンピュータ対戦

  • P1が決定すると、コンピュータは自分に配られたレシートから、乱数で決めた枚数（1〜3枚、残りがなければそこまで）のカードを手札にする。
  • 手札から1枚を選ぶ。本番は GEMINI_API_PLAYER2 のキーでGeminiに選ばせ、デモではPOWER最大のカードで代用する。
  • Geminiには、手札の各カードのID・属性・レア度・HP・ATK・DEF・SPD・LUCK・必殺技倍率だけを渡す。名前・説明文などの文字列は渡さない。P1のカード情報も渡さない。
  • 返答は { "cardId": 数値, "reason": "理由（40文字以内）" }。手札に含まれないIDや形式不正、タイムアウト（20秒）のときは、POWER最大のカードを選び、理由は「自動で選びました」とする。
  • どの場合も新しいカードは生成しない。対戦の前後でカード件数は変わらない。勝敗の計算に補正は入れない。
  • 対戦画面に、コンピュータの選んだ理由を表示する。

9. レシート解析・保存・削除との連動

管理者の操作（既存）カードへの影響
解析応答を返した後、別スレッドでカードを生成して下書きにする。同じ画像のカードがあれば作り直さない。
保存（PostgreSQLへ）下書きが有効になり、対戦で使えるようになる。
削除同じタイミングでカードも削除する（外部キーの連動）。
  • 解析だけして保存しない下書きは、24時間で破棄する。
  • 生成には GEMINI_API_MONSTER を使う。
  • 機能追加前に保存済みのレシートは、リリース時に削除する（カードを持たないレシートを残さない）。
  • 既存の解析・保存・削除の画面と応答は変更しない。

12. セキュリティ

  • 席トークン：128ビット以上の乱数。DBにはハッシュだけ保存する。他席の操作は拒否する。
  • 非公開の徹底：対戦が始まるまで、相手のカード・レシート・手札・選択を、画面にもAPIの応答にも出さない。レシートのAPIはモンスターカードの中身（名前・数値・SVG）を返さない。カードは「選ぶ」APIの応答でだけ、選んだ本人に返す。
  • サーバーでの強制：手札3枚、シャッフルの条件、決定できるカードの範囲を、サーバーが検証する。画面の見た目だけに頼らない。
  • 公開範囲：レシートの内容は、そのルームの席トークンを持つ2人にだけ見せる。一覧・検索・順次取得のAPIは作らない。画像・テーブル名・画像ハッシュ・行テキストは出さない。
  • 回数制限：IPごとに、ルーム作成は10分に5回、参加の試行は1分に10回、画像生成は1日に10回まで。Gemini呼び出しの全体上限（1日あたり、キーごと）を設け、超えたら画像からの生成を止める（既存カードでの対戦は続けられる）。IPはハッシュだけ記録する。1ルームあたりの画像生成回数と、レシートの配布枚数の1日制限は設けない。
  • 画像：JPEG/PNGのみ、5 MiBまで。種類は拡張子ではなく中身で判定する。
  • SVGとGeminiの出力：SVGは許可リスト方式で検証し、スクリプト・外部参照・イベント属性を拒否する。画面の文字列は textContent で表示し、HTMLとして解釈しない。
  • キャッシュ：ゲームのAPIの応答は Cache-Control: no-store。
  • キーの分離：P1の画像生成は GEMINI_API_PLAYER1、P2は GEMINI_API_PLAYER2、解析時の生成は GEMINI_API_MONSTER を使い、混在させない。

13. 非機能要件

項目要件
再現性同じレシート（画像ハッシュ）は常に同じカード。同じ battleSeed と同じ2枚は同じ結果。
応答カード選択画面の表示、シャッフル、選択は1秒以内。画像カードの生成は、Geminiの応答時間に依存する（目安20秒以内）。
可用性Gemini障害時も、既存カードでの対戦は続けられる。
データ保持プレイ用のレシートのコピーは、プレイ終了またはルーム期限切れで削除する。
既存機能への影響既存の解析・保存・削除の画面・API・自動テストは変更しない。
アクセシビリティボタンは disabled で無効を表し、キーボード操作に対応する。進行状況は読み上げに対応する。
テストカード生成・対戦はDOM・DBに依存しない純粋な関数とし、自動テストで確認する。

14. 受入基準

  1. カード選択を開始すると、有効なカードが9枚以上あるとき、レシートが3×3で9枚並ぶ。8枚以下なら全件が並ぶ。
  2. 有効なカードが10件以上のときだけ、「シャッフル」が表示され、押すと別の9枚に変わる。9件以下では表示されない。
  3. レシートの表示に、行テキストが含まれない。
  4. 各レシートの「このレシートを選ぶ」ボタンが、同じ行で下端にそろって表示される。
  5. レシートを1枚選ぶと、シャッフルが無効になる。
  6. 手札が3枚になると、シャッフル・各レシートの選択・2つのタブが無効になる。4枚目はサーバーが拒否する。
  7. 「レシート画像から作る」で作ったカードは1体だけ表示され、作り直すと置き換わる。3枚の上限・生成回数の表示は出ない。そのカードで決定・対戦できる。
  8. 手札・画像カード以外のカードの決定は拒否される。
  9. 相手のカード・レシートは、対戦開始まで画面にもAPIの応答にも出ない。
  10. P2が参加しないまま待機が終わると、コンピュータ対戦になり、新しいカードは生成されない（件数が変わらない）。
  11. 同じ battleSeed と同じ2枚で、結果が同じになる。
  12. 管理者が解析・保存・削除すると、カードが下書き・有効・削除に連動して変わる。既存画面は変わらない。
  13. 回数制限を超えると429が返り、既存カードでの対戦は続けられる。

15. デモとの差異・未決事項

項目デモ本番
データ架空のレシート12件（解析前の2件を含む）をブラウザー内に持つDBの receipt_structured_summary ／ receipt_structured_item から読む
相手自動操作（人間役もコンピュータ役も同じ画面内）別PCの人間。ルーム・勝敗はサーバーが管理
待機時間12秒既定90秒（設定で変更可）
画像カード画像のハッシュから架空のレシートを作るGeminiが画像を読み取り、構造化データを作る
コンピュータの選択POWER最大のカードGeminiが手札から選ぶ
表示の列数3列固定幅に応じて調整してよい

未決事項

  • 「有効なカードが8枚以下」の扱い（全件表示とした）を、9枚ちょうどのときと合わせて確認する。
  • 手札3枚で画像タブが無効になる（画像カードを使えなくなる）のは意図どおりか。画像側を常に使えるようにする案もある。
  • 手札が3枚になったとき、画像タブを開いたままだと手札の一覧に戻れない。「レシートを選ぶ」タブだけ有効のままにするか。
  • 3枚選ぶのが最善になり、駆け引きが減る。「選ぶほど不利になる」ルールを別途検討するか。
  • レシートに写る個人情報（氏名・電話番号など）が、構造化データの項目に含まれる場合の扱い。
