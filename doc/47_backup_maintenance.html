1. バックアップ対象

対象要否理由
receipt_*、receipt_structured_*、receipt_image_hash_registry必要保存済みレシート（画像は保存していない）
monster_card必要カード（イラスト含む）。再生成すると同じ名前/能力値だがイラストが変わる
monster_room/play/battle不要一時データ
環境変数/シークレット別管理39
元のレシート画像アプリでは保管しない必要なら管理者側で保管

2. バックアップ手順（例）

Render PostgreSQL の自動バックアップ・保持期間はプランに依存します。利用プラン（現状は無料プラン）での提供内容を確認してください。以下は一般的な pg_dump の例で、接続情報は環境変数から与え、手順書やシェル履歴に値を残さないこと。
PGPASSWORD="$DB_PASSWORD" pg_dump -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" -Fc -f receipt_game_$(date +%Y%m%d).dump

3. リストア手順（例）

  1. 失われるデータ（バックアップ以降に保存したレシート）を確認する。
  2. バックエンドを停止（実際の稼働形態を確認してから。44）。
  3. 空のDBへ pg_restore -d <DB> <dump>。既存DBへ戻す場合は事前に別名で退避。
  4. バックエンドを起動し、テーブルが作成/整合すること、/api/health、一覧表示、対戦を確認。
  5. 必要なら起動時バックフィルでカードを補完。

4. 定期メンテナンス

周期作業
毎日ログ・ヘルス確認
月次ログのZIPの容量確認と古いものの整理、Gemini利用量の確認、月次報告
四半期依存ライブラリの更新確認（Spring Boot等）と mvn test、APIキーのローテーション検討
随時管理者パスワード変更、不要レシートの削除（自動削除はしない）

実施者は開発者本人。実施日は作業のたびに記録する。

5. 保持方針

画像：保存しない。レシート：管理者が削除するまで保持。下書きカード：24時間。ルーム：操作なし120分で失効、閉鎖後10分保持。ログ：日次ZIP（保持期間は未定義）。
