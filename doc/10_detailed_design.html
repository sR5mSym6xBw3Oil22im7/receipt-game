2. レシート解析（POST /api/receipts/analyze）

  1. ReceiptUploadValidator：空・5MiB超・Content-Type（JPEG/PNG）・先頭バイト・画素数（上限25,000,000）を検査
  2. SHA-256を計算し、GeminiReceiptAnalyzer で解析（GEMINI_API_ANALYZE、失敗かつ特定コードなら GEMINI_API_DEFAULT で再試行）
  3. JSONスキーマ指定で lines と structuredData、textRotation を受け取る。90/180/270度の回転指定があれば画像を回して読み直し、行数が多い方を採用（12,000,000画素超は回さない）
  4. reserveImageHash でハッシュを予約（保存済みなら409）
  5. prepareDraftAsync：応答後に別スレッドでカード下書きを作る（応答は変えない）
解析ではレシート用テーブルを作らない（analyzeDoesNotCreateReceiptTable）。

3. レシート保存（POST /api/receipts/save）

  1. lines が空なら400 EMPTY_RECEIPT、sha256 は64桁16進以外なら400 INVALID_IMAGE_HASH
  2. PersonalInfoSanitizer で個人情報を「（非表示）」に置換。失敗時はカードも作らず保存しない（422 PERSONAL_INFO_CHECK_FAILED）
  3. トランザクションの外でカードを準備（Gemini呼出しは時間がかかるため）：MONSTER キー → DEFAULT キー → 計算式と代替イラスト
  4. トランザクション内で receipt_<uuid> 作成・行挿入・構造化データ保存・カードの有効化を一括コミット

4. カード生成の優先順位

順内容
1GEMINI_API_MONSTER でパラメータとSVGイラストを生成
2失敗なら GEMINI_API_DEFAULT で再試行
3両方失敗なら計算式の値＋代替イラスト（MonsterCardGenerator.generate）
  • AIのパラメータは applyParameters で範囲に収める（名前はカタカナ12文字以内、説明は80文字以内、URL風文字列は不採用）。POWER・レア度・店種ボーナスはサーバーで再計算。
  • SVGは MonsterSvgValidator の許可リスト検証（長さ≤30,000、要素≤300、深さ≤12、サイズ≤1000、スクリプト・外部参照・イベント属性・コメント禁止）。不合格は代替イラスト。

5. ルーム進行（MonsterRoomService）

処理要点
排他各操作で SELECT … FOR UPDATE（lockByCode）によりルーム単位で直列化
席の認可トークンのハッシュ（SHA-256）と照合。ルームなし・席なしはどちらも403 SEAT_REQUIRED（存在を推測させない）
配布対人：有効カードをシャッフルしP1/P2へ最大9枚ずつ。CPU：CPUに1枚、プレイヤーに最大9枚
CPU手札1〜3枚（乱数）からGemini（PLAYER2キー）で選択、失敗時はPOWER最大。非同期実行（MonsterTaskRunner 2スレッド）
対戦開始双方決定で startBattle：シードを生成し MonsterBattleEngine.battle を実行、結果を monster_battle に保存
画像カード状態確認→（行ロックを持たず）Gemini→登録。既存の有効カードがあれば再利用（reused=true）。1体のみ
掃除@Scheduled：ルーム5分ごと、下書きカード10分ごと（24時間超を破棄）

6. 例外処理

業務エラーは ReceiptException(status, code, message)、予期しない例外は INTERNAL_ERROR（詳細はログのみ）。一覧は 15 API仕様書 5章。

7. ログ

  • logging.file.name: log/backend.log、日次・サイズでZIPローテーション。
  • APIキー・画像本文・個人情報はログに出さない方針（例：個人情報除去は件数のみ count=2 のように記録）。
