1. 目的と概要

DBに保存済みのレシートデータから「モンスターカード」を自動生成し、2人のプレイヤーがそれぞれのカードで対戦する「モンスターレシート対戦ゲーム」を、既存のレシート解析システムに追加する。ゲームの着想は「バーコードバトラー」である。バーコードの代わりに、レシートの店舗・商品・金額・購入時刻などを元にモンスターの強さと姿が決まる。

2人対戦プレイヤー1・2は別々のPC
解析時に生成レシート解析のたびにカードを作成
SVGカードとイラストはSVGで生成
ログイン不要プレイヤーは管理者ログインなしで遊べる
サーバー判定勝敗はサーバーで計算（不正防止）

原則として、対戦にはレシート解析時に作成済みのカードを使う。ただし、プレイヤーは対戦中にレシート画像を取り込んで自分専用のカードを新しく生成してもよい（8章）。

責務の分担（公平性の要）

  • 数値（HP・攻撃・防御・素早さ・運・レア度・属性・必殺技倍率）：レシートの構造化データからプログラムが決定的に計算する。Gemini は関与しない。
  • 見た目（名前・説明文・SVGイラスト）：Gemini が生成する。失敗・不正出力の場合は、ハッシュから作る代替SVGと代替名に切り替える。

この分担により、AIの気まぐれでカードの強さが偏ること、プロンプト操作で強いカードを得ることを防ぐ。同じレシートからは常に同じ強さのカードができる。

5. モンスターカード生成アルゴリズム（Claude Opus案）

5.1 入力

既存の構造化データ（ReceiptStructuredData）、解析で得た行テキスト、画像のSHA-256（image_sha256）を使う。金額だけでなく、次の6種類の要素を混ぜて強さを決める。

記号要素0〜1への換算
A合計金額 total（未設定なら商品金額の合計）min(total, 30000) / 30000
M最も高い商品の金額 maxAmountmin(maxAmount, 10000) / 10000
C文字数（解析で得た全行の文字数。改行・空白を除く）min(chars, 600) / 600
N商品数（名前が空の行を除く）min(itemCount, 20) / 20
T時刻帯（購入時刻の「時」。未設定は12時）min(12, abs(hour − 12)) / 12（朝・夜ほど大きい）
W日付（購入日の日と曜日）(day − 1) / 30 × 0.7 ＋ (土日なら 0.3)
R0〜R5画像ハッシュのゆらぎ（seed32 ＝ SHA-256 の先頭8桁を整数化し、5ビットずつずらして1バイトを取る）((seed32 >>> (k×5)) & 255) / 255

同一レシート＝同一カードは変わらない（入力が同じなら結果も同じ）。

5.2 属性

商品カテゴリごとの金額を合計し、最も多いカテゴリで決める。同額なら先に現れたほうとする。商品が1つもなければ「無」。

商品カテゴリ（既存の解析結果）属性イメージ
飲食炎調理の火、ホットな外食
食料品土大地の恵み
日用品風軽やかな暮らしの道具
交通・移動雷疾走、電気
その他／未知の値無得意も不得意もない

5.3 ステータス（基礎値）

各ステータスは、複数の要素の重みつき平均で決める。金額（AとM）の重みは、どのステータスでも0.25以下とする。

HP   = 200 + floor( 500 * (0.25A + 0.30C + 0.15N + 0.15W + 0.15R0) )   // 200〜700
ATK  =  40 + floor( 100 * (0.25M + 0.25C + 0.15T + 0.15W + 0.20R1) )   // 40〜140
DEF  =  30 + floor(  80 * (0.15A + 0.30N + 0.20C + 0.15W + 0.20R2) )   // 30〜110
SPD  =  40 + floor(  60 * (0.35T + 0.20W + 0.15C + 0.10N + 0.20R3) )   // 40〜100
LUCK =   5 + floor(  20 * (0.50R4 + 0.25W + 0.25C) )                   // 5〜25（会心率 %）
ステータス金額の重み金額以外の重み
HP0.25（A）文字数 0.30、商品数 0.15、日付 0.15、ゆらぎ 0.15
ATK0.25（M）文字数 0.25、時刻帯 0.15、日付 0.15、ゆらぎ 0.20
DEF0.15（A）商品数 0.30、文字数 0.20、日付 0.15、ゆらぎ 0.20
SPD0時刻帯 0.35、日付 0.20、文字数 0.15、商品数 0.10、ゆらぎ 0.20
LUCK0ゆらぎ 0.50、日付 0.25、文字数 0.25
金額帯を推測されないための考え方：金額が極端に変わっても、各ステータスの変動はその範囲の25%以下（例：HPなら最大125、ATKなら最大25）にとどまり、ほかの要素とゆらぎに隠れる。したがって、カードの数値から元レシートの金額帯を確実に言い当てることはできない。この上限は自動テストで確認する（17章）。

5.4 補正

適用順は「店舗補正 → ラッキーボーナス」。「×1.10」は整数演算（floor(値 × 11 / 10)）で行い、浮動小数点の誤差を避ける。

条件補正
店舗カテゴリ＝スーパーHP ×1.10（小数切り捨て）
コンビニSPD ×1.10
ドラッグストアDEF ×1.10
飲食店ATK ×1.10
その他LUCK ＋3
ラッキーボーナス：次のどれかに当てはまる ①合計金額が111以上で全桁が同じ数字（111、2222 など）、または1000で割った余りが777 ②購入時刻の時と分が同じ（11:11、22:22 など） ③購入日が7日・17日・27日ATK・DEF ×1.10、LUCK ＋10（バーコードバトラーの「当たり」に相当）

画面には「ラッキー」の印だけを出し、どの条件で付いたかは示さない（金額がゾロ目であることを知られないため）。

5.5 総合力とレア度

POWER = floor( HP/5 + ATK + DEF + SPD/2 + LUCK*2 )

N  : POWER < 275
R  : 275 〜 314
SR : 315 〜 344
SSR: 345 以上

金額が影響する割合を抑えたため、強さの分布は中央に寄る。基準値は、乱数による試算（4,000件）で N 約25%・R 約40%・SR 約25%・SSR 約10% になるよう決めた仮値で、本番の実データで見直す。レア度は演出（カード枠の色）と対戦ルールには影響しない。強さは数値そのもので決まる。

5.6 必殺技

  • 必殺技倍率 ＝ 1.5 ＋ 0.5 × (0.2M ＋ 0.4C ＋ 0.4R5)（小数第2位に四捨五入、1.50〜2.00）。金額（M）の重みは0.2。

5.7 名前・説明文・SVGイラスト（Gemini）

Gemini には、属性・レア度・ステータス・店舗カテゴリ・代表的な商品名（最大3つ）だけを渡す。店名・支店名・金額・レシート番号・画像は渡さない。（プレイヤーが画像から作る場合は、画像の解析に画像そのものを使うが、カード生成の呼び出しには同じ最小限の情報だけを渡す。）Gemini は次のJSONを返す（構造化出力）。

{ "name": "モンスター名（全角12文字以内）",
  "flavorText": "説明文（60文字以内）",
  "svg": "<svg viewBox=\"0 0 200 200\" ...>...</svg>" }

SVGは13章の検証を通ったものだけを採用する。次のいずれかの場合は代替生成に切り替え、illustration_source = 'FALLBACK' として記録する。

  • Gemini 呼び出しの失敗・タイムアウト（60秒）、JSONの形式不正
  • SVGの検証失敗（禁止要素、20 KB超過、viewBox 不一致）
  • 名前の空文字・長さ超過

代替生成：属性ごとの体の形（炎＝しずく型、土＝丸型、風＝雲型、雷＝角型、無＝円）に、目・角・足の数と色をseedから決めて組み立てる。名前は「属性別の接頭辞4種 × 接尾辞6種」から選ぶ。これにより、AIが使えなくてもカードは必ず作れる。デモ画面のイラストはこの方式で描いている。

5.8 版管理

アルゴリズムを変更しても過去のカードの数値は変えない。カードには algorithm_version（現行＝2。版1は金額中心の初期案で、実装前に廃止）を保存する。

6. 対戦・勝敗判定アルゴリズム（Claude Opus案）

6.1 基本方針

  • 1対1、1枚ずつのターン制。1発勝負（1回の対戦で決着し、再試合・三本勝負はない。同じルームでの「再戦」は新しい別の対戦として扱う）。
  • 対戦はサーバーが計算する。ブラウザーは受け取ったターン記録を再生するだけで、結果を送らない。
  • 乱数はサーバーが対戦開始時に作る battleSeed（32ビット）から発生させる。同じ入力から同じ結果を再現できる（調査・不具合再現用）。

6.2 手順

  1. 両者のHPを最大値にする。
  2. 先攻決定：SPDが高いほうが先攻。同値なら battleSeed の最下位ビットが0ならP1。
  3. ラウンド1〜20を繰り返す。各ラウンドで先攻、後攻の順に1回ずつ行動する。相手のHPが0になったら、その時点で対戦終了（後攻は行動しない）。
  4. 各プレイヤーの3回目ごとの行動は必殺技、それ以外は通常攻撃とする。
  5. 行動ごとに乱数を2つ引く（①ダメージのばらつき、②会心判定）。
基本値   = max( 1, ATK × 技倍率 − DEF(相手) × 0.5 )     // 通常攻撃＝1.0、必殺技＝skillPower
ばらつき = 0.9 + 0.2 × rand()
属性相性 = 有利 1.25 ／ 不利 0.80 ／ その他 1.00
会心     = rand() < LUCK / 100  →  ×1.5
ダメージ = max( 1, round( 基本値 × ばらつき × 属性相性 × 会心 ) )

乱数 rand() は mulberry32（battleSeed を初期値とする1本の列）を、行動の順番どおりに消費する。

6.3 属性相性

炎 → 風 → 土 → 雷 → 炎   （矢印の先に対して有利。逆向きは不利）
無は常に等倍

6.4 勝敗

順位条件結果
1相手のHPを0にした勝ち
220ラウンド終了時、残りHP割合（現在HP÷最大HP）が高い判定勝ち
3割合が同じ場合、POWERが高い判定勝ち
4それも同じ引き分け

残りHP割合で比べるため、HPの大きいカードが一方的に有利にならない。

デモで12枚のカード総当たり×各20シードを試算したところ、すべてKO決着（平均8回の行動）だった。20ラウンドの上限と判定は、極端に硬いカード同士の場合の安全装置である。

6.5 保存する対戦記録

battleSeed、両カードID、ターンごとの記録（行動者・技・ダメージ・会心・残りHP）、勝者、終了理由（KO／判定）。

7.2 リリース時：追加前に保存したレシートの削除

この機能の追加前に保存したレシートは、カードを持たないため、リリース時に削除する。削除は元に戻せないので、次の手順で行う（本書の作業ではDBを操作していない）。

  1. 削除対象を確認する：既存の「保存済みレシートを確認する」画面で、リリース前に保存された一覧を控える。
  2. 必要なら、PostgreSQLのバックアップ（pg_dump）を取る。
  3. 新機能（フィルターと新テーブル）を有効にする前に、既存の「レシート削除」機能で対象を削除する。既存機能の操作だけで行い、SQLで直接消さない（画像ハッシュ・構造化データも既存の処理で消えるため）。
  4. 一覧が空になったことを確認してから、新機能を有効にする。
  5. 以降に解析・保存したレシートが、カードの元になる。

削除後は、画像ハッシュの登録も消えるため、同じ画像を解析し直して保存できる（そのときに、カードも作られる）。

実装時の注意：既存の構造化データ用テーブルは、最初の保存時に実行時作成される。新テーブルは外部キーなしで先に作り、既存テーブルが存在した時点で外部キーを追加する（既存コードが自分の外部キーを追加している方法と同じ）。

8. 対戦時のカード生成（レシート画像から）

  1. ログインなしのプレイヤーが対戦中の画面でレシート画像（JPEG/PNG、5 MiB以下）を選ぶ。
  2. サーバーが SHA-256 を計算する。既にカードがある画像なら、新規生成せず既存カードを返す（同じ画像で何枚も作る不正を防ぐ）。ただし、返すのは ACTIVE（管理者が保存済みのレシート）か、同じルームの TEMP に限る。DRAFT は返さない。
  3. 新しい画像なら、画像を読み取る。既存の GeminiReceiptAnalyzer は、起動時に GEMINI_API_ANALYZE のキーを固定して持つため、再利用しない（再利用すると、既存の解析のキーの取り扱いを変えることになる）。新規のクラスが、既存と同じ手順（同じモデル・同じ検証）で、別のGeminiクライアントを作って呼び出す。キーは操作者の席で決まる：P1は GEMINI_API_PLAYER1、P2は GEMINI_API_PLAYER2。
  4. 5章のアルゴリズムでカードを生成する（見た目のGemini呼び出しも同じ席のキー）。
  5. カードを monster_card（source = 'PLAYER1' または 'PLAYER2'、status = 'TEMP'）へ保存する。画像ファイルは保存しない（既存方針と同じ）。この種のカードはレシートDBに結びつかず、他のプレイヤーには配られない。ルームの期限切れ（24時間以内）で削除する。
  6. 生成したカードは、そのルームの自分の枠に自動でセットされる。
既存機能との関係：この処理は既存の「レシート解析」画面・APIを経由しない。新規のAPI内で、新規のクラスが画像を解析する。既存の GEMINI_API_ANALYZE の使い方は変わらない。解析のみを行い、既存の receipt_* テーブルには保存しない。

1席あたりの生成回数は、1ルームにつき3回までとする（利用上限対策）。画像から作ったカードも、手札12枚の1枚に数える（9.0）。画像が既存の有効なカードと同じ場合は、そのカードを手札に入れる（ただし、相手に配られているカードは使えない）。コンピュータ（P2）の席は、この機能を使えない（コンピュータのカードは既存カードから選ぶだけ。9.1）。

13. セキュリティ要件

プレイヤーは管理者ログインなしで遊べる。誰でもアクセスできるため、「公開APIが悪用されないこと」と「管理者のレシート情報が漏れないこと」を最優先にする。

ID要件
S-01SVGの検証（保存前・必須）：許可リスト方式。許可要素は svg、g、defs、path、circle、ellipse、rect、line、polyline、polygon、linearGradient、radialGradient、stop、clipPath、title。許可属性は図形・塗り・線・変形・グラデーション関連のみ。
S-02script、foreignObject、image、use、style、animate系、on* 属性、href／xlink:href、外部を指す url(、javascript:、DOCTYPE／ENTITY（XXE対策）を拒否する。XMLパーサーは外部実体を無効にする。
S-03SVGは20 KB以下。viewBox は 0 0 200 200 固定。
S-04画面では、検証済みSVGを <img src="data:image/svg+xml..."> で表示する（スクリプトが実行されない経路）。名前・説明文はテキストとして扱い、HTMLとして挿入しない。
S-05Gemini APIキーは .env（環境変数）から読み、画面・API応答・ログ・DB・ソースコード・本書に出さない。用途別キーを使い分ける（2章の表）。カード生成は GEMINI_API_MONSTER、レシート解析は GEMINI_API_ANALYZE。
S-06認可の分離：公開するのは /api/monster/** だけ。既存の SecurityConfig は編集せず、/api/monster/** 専用の SecurityFilterChain（@Order(1)）を新規ファイルで追加し、/api/receipts/**・/admin/** の認可（管理者限定）には一切触れない。ゲームのAPIから既存のレシートAPIや管理者の権限へ到達できない。
S-07席トークン：128ビット以上の乱数。DBにはハッシュのみ。他席の操作（相手の選択・確定）は拒否する。ルームコードは英数字6桁（紛らわしい文字を除く32種）で、推測だけでは席を奪えない。
S-08相手のカードは、対戦が始まるまで内容（ステータス）を返さない（後出しを防ぐ）。
S-09画像アップロードは既存と同じ検証（JPEG/PNG、5 MiB、マジックナンバー確認）を行う。画像は保存しない。
S-10Geminiに渡す情報から店名・金額・レシート番号を除く（5.7）。
S-11回数制限（ログインなしで悪用されないため）：IPごとに、ルーム作成は10分に5回、ルーム参加の試行は1分に10回、画像生成は1日に10回まで。1ルームあたりの画像生成は1席3回まで。レシートの配布・追加は、1プレイで12枚までとし、1日あたりの枚数制限は設けない（決定事項）。Gemini呼び出しの全体上限（1日あたり、キーごと）を設け、超えたら画像からの生成を止める（配布済みのカードでの対戦は続けられる）。回数の記録にはIPのハッシュだけを使う。
S-12レシート情報の公開範囲（決定事項）：管理者のレシートのすべての内容（構造化データの全項目と、解析の行テキスト）を、ゲームプレイヤー1・2に限定して表示する。限定の意味は次のとおり。① 見せる相手は、そのルームの席トークンを持つ2人だけ。席トークンのない人、別のルームの人には出さない。② 対戦が始まるまでは配られた本人にだけ、対戦が始まったあとは選ばれた2枚の元レシートを両プレイヤーに見せる（9.0）。③ 1プレイで見せるのは最大12枚（相手の分を除く）。④ 出さないもの：画像、テーブル名、画像ハッシュ。⑤ 全レシートを一覧する・検索する・順に取得するAPIは作らない。⑥ 画面に出したレシートの内容は、公開ログ・対戦履歴の一覧には含めない。DBの monster_card には、これらの値を保存しない（配布時に既存テーブルから読み、プレイ用に一時コピーするだけ。ルームの期限切れ・プレイ終了で削除）。
S-13CSRF：ゲームのAPIは Cookie に頼らず、席トークンをヘッダー（X-Seat-Token）で送る。Cookieで認証しないため、他サイトからの勝手な操作は成立しない。ルーム作成・参加は、カスタムヘッダー必須とし、Origin が許可されたフロントエンドのときだけ受け付ける（CORSは許可したオリジンのみ）。
S-14入力検証：ルームコード・カードID・画像・ページ番号はすべてサーバーで検証し、SQLはプレースホルダーを使う。エラーメッセージに内部情報（例外、SQL、パス）を出さない。
S-15解析フィルターの安全性：既存応答を書き換えない。例外は握りつぶして記録する。生成の失敗で既存の解析・保存・削除が失敗しない。フィルターが読む応答・要求に含まれるレシート本文はログに出さない。
S-16通信はHTTPS。レスポンスに X-Content-Type-Options: nosniff、Cache-Control: no-store（ルーム系）を付ける。
S-17ルーム・TEMPカード・DRAFTは期限で自動削除する。席トークンのハッシュとIPのハッシュも、ルームと一緒に削除する。
S-19コンピュータによる新規生成の禁止（強制）：コンピュータ対戦の処理は、monster_card から ACTIVE のカードを読むだけにする。カード生成を行うクラス（解析時生成、画像からの生成）を呼び出さない。コンピュータ対戦のDBアクセスは参照専用の関数に限り、カードの追加・更新の関数を持たせない。自動テストで、コンピュータ対戦の前後で monster_card の件数が変わらないこと、Geminiへの呼び出しが「選択」の1種類だけ（SVGや画像を扱う呼び出しがない）ことを確認する。TEMP（プレイヤーが画像から作った一時カード）と DRAFT は候補にしない。
S-20コンピュータの思考への入力・出力の安全性：Geminiへの入力は数値・ID・属性・レア度だけ（文字列の生成物を含めない）。出力は構造化出力で受け、IDが候補にあるか、理由が40文字以内の文字列かを検証する。理由は textContent で表示する。検証に失敗したら規則で選ぶ。
S-21コンピュータの思考のGemini呼び出しも、S-11のキーごとの1日の全体上限に含める。上限に達したら規則で選び、対戦は続けられる。切り替わりを悪用してGeminiを呼ばせる目的でルームを乱立させる行為は、ルーム作成の回数制限（S-11）で防ぐ。
S-22伏せたモンスターの秘匿と枚数の強制：レシートのAPIは、モンスターカードの中身（名前・数値・SVG）を返さない。カードは、レシートを選ぶAPIの応答でだけ、選んだ本人に返す。引いた枚数（12枚まで）・手札・選択はサーバーが管理し、13枚目の追加、手札にないカードの選択、他人に配られたレシートの取得・選択を拒否する。画面の見た目だけに頼らない。
S-23公開する内容の取り扱い：レシートの行テキストには、電話番号・会員番号・住所などが含まれる可能性がある。これらも、決定事項（S-12）のとおり、ゲームプレイヤー1・2にだけ表示する。画面に出す文字列はすべて textContent で表示し、HTMLとして解釈しない。応答はキャッシュさせない（Cache-Control: no-store）。
S-18金額帯の推測の防止：金額（A・M）の重みは各ステータスで0.25以下（5.3）。「ラッキー」の印は金額以外の条件でも付く（5.4）。

R-06この機能の追加前に保存したレシートを削除すると、元に戻せない。7.2の手順（一覧の控え、バックアップ、既存の削除機能で削除、空になったことの確認）を、リリース手順書に追記する（本番実装時）。
R-10有効なカードが2枚未満だと、レシートを配れず対戦できない。9.0：理由を表示してルームを終了。対戦できるカードが一定数あることを、運用の前提とする。
R-11待ち時間90秒は、友人が参加するには短いことがある。設定値（MONSTER_CPU_WAIT_SECONDS）で変更できる。仮値であり、実際の使われ方を見て見直す。
R-12コンピュータが有利になりすぎないか。コンピュータも人間と同じく、レシート1枚から始め、最大12枚まで、中身を見ずに引く。引く枚数は乱数。勝敗の計算には補正を入れない。
R-1512枚まで引けるため、毎回12枚引いて最強のカードを選ぶのが最善になる。ゲームとしての駆け引きが減る。仕様どおり（決定事項）。調整するなら、「引くほど不利になる」ルール（例：引いた枚数に応じて選んだカードのHPを下げる）を別途検討する。
R-161日の配布制限がないため、短時間に多数のルームを作って、大量のレシートの内容を取得される。ルーム作成のIP別制限（S-11）が唯一の歯止め。必要なら、後から全体の配布上限（例：1日あたりの合計枚数）を追加できる設計にする。
R-1712枚のうち相手と取り合いになり、有効なカードが少ないと、後から引く側が不利。配布は重ならない。残りがなくなれば、引けない。有効なカードが十分あることを運用の前提とする。
R-14配られたレシートの内容（店舗カテゴリ・金額・商品）から、モンスターの強さを予想される。見られるのは本人のレシートだけで、ゲームの楽しさ（どんなレシートがどんなモンスターになるか）の一部として許容する。強さは金額だけでは決まらない（5.3）。
R-09金額の影響を抑えたため、強さの差が小さくなる。レア度の基準値は仮値。本番の実データで見直す（5.5）。
R-07フィルターで観測する方式は、既存のAPI応答の形式が変わると動かなくなる。応答の形式をテストで固定し、フィルターは解釈に失敗したら何もしない（既存機能は影響を受けない）。
R-08無料枠のサーバー停止で、進行中のルームが失われる。ルームは短い期限のものとして扱う。再作成すれば遊べる。

17. 受入基準

  1. 管理者が既存の「レシート解析」を実行すると、解析の応答が従来どおり返り、そのあとカードが下書きとして作られる。
  2. 「保存」するとカードが対戦で使える（配布の対象になる）。保存しないカードは配られない。
  3. 「レシート削除」をすると、同時にそのカードも消える（配布の対象から消え、対戦履歴は読める）。
  4. 同じレシートからは常に同じ数値のカードができる。同じ画像を再解析してもカードは増えない。
  5. 金額の影響の上限：金額（合計・最高額）だけを変え、ほかの条件を同じにしたとき、HP・ATK・DEF の変動はそれぞれ範囲の25%以下（HP 125、ATK 25、DEF 12）、SPD・LUCK は変わらない。日付・時刻帯・文字数を変えると、各ステータスが変わる（自動テストで確認）。
  6. 公開APIの応答とDBの monster_card に、金額・日付・時刻・文字数が含まれない。
  7. カード生成の Gemini 呼び出しは GEMINI_API_MONSTER のキー、既存のレシート解析は GEMINI_API_ANALYZE のキーを使い、既存の解析の挙動が変わっていない（テストで確認）。
  8. レシート1枚から始める：プレイ開始時、各プレイヤーにレシートが1枚だけ配られ、そのレシートの全項目（店名・日時・商品・金額など）が本人にだけ表示される。モンスターカードは表示されず、APIの応答にも含まれない。
  9. レシートを選ぶと、そのモンスターカードが現れ、手札に入る。「レシートを追加で引く」で、画像から作るカードを含めて合計12枚まで増やせる。13枚目はサーバーが拒否する。1日あたりの枚数制限はない。手札にないカードは選べない。
  10. レシート1枚だけでも、手札（1〜12枚）から1枚を選んで対戦できる。2人に配られるレシートは重ならない。
  11. 対戦が始まるまで、相手のレシートの内容は画面にもAPIの応答にも出ない。対戦が始まったあとは、選ばれた2枚のカードの元レシートの全内容（行テキストを含む）が、両プレイヤーに表示される。席トークンのない人には、どの内容も返らない。図鑑の画面・APIは存在しない。
  12. コンピュータ対戦：P1がルームを作り、待ち時間内にP2が参加しないと、コンピュータ（P2）との対戦に切り替わる。切り替え後の参加は409になる。参加と切り替えが同時でも、どちらか一方だけが有効になる。
  13. コンピュータは、人間と同じくレシート1枚から始め、追加で引いた手札（最大12枚）から1枚を選ぶ。選ぶカードは、DB上の ACTIVE のカードである。コンピュータ対戦の前後で monster_card の件数が変わらない（新規生成が起きない）。
  14. コンピュータの思考のGemini呼び出しは GEMINI_API_PLAYER2 のキーを使う。Gemini失敗時・上限時は規則で選び、対戦を続けられる。
  15. 画面・結果・履歴で、相手がコンピュータであることが分かる。
  16. リリース時、追加前に保存したレシートが既存の削除機能ですべて削除され、一覧が空になっている。
  17. Geminiを止めても、代替SVGでカードができる。不正なSVGは保存されない。
  18. ログインしていない別々のPCで、P1がルームを作り、P2がコードで参加し、それぞれカードを選んで1発勝負で対戦できる。
  19. 両PCで同じ対戦内容・同じ勝敗が表示される。同じ battleSeed の再計算で同じ結果になる。
  20. 解析時の生成は GEMINI_API_MONSTER、P1の画像生成は GEMINI_API_PLAYER1、P2は GEMINI_API_PLAYER2 を使う（テストで確認）。
  21. ログインなしで /api/receipts/**・/admin/** にアクセスすると従来どおり拒否される。ゲームのAPIの応答に、テーブル名・画像・画像ハッシュが含まれない。レシートの内容（行テキストを含む）は、席トークンを持つプレイヤーへの応答にだけ含まれ、DBの monster_card には保存されない。
  22. 回数制限を超えると429が返り、配布済みのカードでの対戦は続けられる。
  23. 既存の3機能の画面・API・自動テストが従来どおり動く。既存ファイルの差分がない。
  24. 既存画面のデザインが変わっていない。新画面が金貨テーマで表示される。
