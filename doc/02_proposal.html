1. 作品の概要

レシート画像のAI解析とモンスター対戦を組み合わせたWebゲームを、フロントエンド（静的ページ）とバックエンド（Spring Boot）の2層構成で個人開発しました。バックエンドはDockerで動作し、Renderへデプロイできる状態にしてあります。本書では、技術の選び方と、設計・実装で工夫した点をまとめます。

3. 技術選定と理由

領域採用理由
言語・FWJava 21 / Spring Boot 4.1.0 / Spring Security 7.1.0セキュリティ（CSRF・セッション・ヘッダー）の標準機能、トランザクション管理、テスト基盤が揃う
DBPostgreSQL（本番Render、ローカルはDocker）レシートごとのテーブル作成、トランザクション、FOR UPDATE によるルームの排他
AIGoogle Gemini（gemini-3.5-flash-lite）画像入力とJSONスキーマ指定の構造化出力に対応。軽量モデルで応答が速い
フロントビルド不要の静的HTML/CSS/JavaScript（GitHub Pages）配信と運用が単純で、ビルド手順・依存が不要
テストJUnit（H2）、node:testPostgreSQLやGeminiなしで mvn test が実行できる

代替案の検討と詳細は 09 基本設計書 と 11 システム構成図 を参照。

4. アピールポイント（設計・実装で工夫した点）

観点工夫した点詳細
サーバー主導の対戦勝敗・カード生成はすべてサーバーで計算。相手のカードは対戦開始まで応答に含めない。同じシードと同じ2枚なら必ず同じ結果05、10、17
決定論的なカード生成画像のSHA-256を乱数の種にして能力値を計算。同じレシートからは同じ名前・能力値のカードができる。デモ画面のエンジンとの一致をテストで検査05、28
AIの失敗を前提にした設計解析はキー用途別に再試行、カード生成は計算式の値と代替イラストへ自動で切り替え。AI出力は範囲に丸め、SVGは許可リストで検証10、17
個人情報への配慮保存前に氏名・電話番号・住所・メール・会員番号・カード番号を「（非表示）」に置換。取り除けなければ保存しない。画像そのものは保存しない17、51
セキュリティ/api/** を既定拒否、CSRF、ログイン失敗ロック、アップロードの型・画素数検査、IP別のレート制限、CSP等のヘッダー17、33
テストと検証バックエンド180件・フロント31件の自動テスト。セルフレビューで34件を指摘し、PoCで再現確認のうえ修正29、30、33
文書化要件・設計・テスト・運用の文書56点。実施していない項目は「未実施」と明記55

5. 前提条件・制約

  • Gemini APIキーは開発者自身のものを使う。利用料・クォータはGoogleの規約に従う。
  • Renderの無料プランを使うため、無活動時の停止・起動待ち、DBの保持期間などはRenderの仕様に従う（render.yml で plan: free）。
  • 対応するレシート画像はJPEG/PNG（最大5 MiB）。ZIPはJPEG/PNGのみのもの。
  • 管理者は1名（環境変数で設定）。複数管理者・権限管理は範囲外。

7. 今後の課題

  • 負荷試験は、本番環境がGitHub PagesとRender無料プランのため実施不可。第三者によるセキュリティ診断は今後の課題、実機ブラウザーでの網羅確認は未実施（31、32、33）。
  • ログイン失敗やレート制限の記録がメモリ上のため、複数インスタンス化するときは共有ストアが必要。
  • 監視ツール・通知の導入、依存ライブラリの継続的な脆弱性スキャン。
