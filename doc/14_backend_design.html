2. 解析処理

  1. ReceiptUploadValidator で空・大きさ・Content-Type・先頭バイト・画素数を検査する。
  2. 画像のSHA-256を計算する。
  3. GeminiReceiptAnalyzer が GEMINI_API_ANALYZE で解析する。キー・上限・APIの失敗、応答の形式不正なら GEMINI_API_DEFAULT で読み直す（同じキーなら読み直さない、NO_TEXT_FOUND は読み直さない）。
  4. Geminiが推定した回転角（90・180・270）があれば画像を回して再解析し、行数が多い方を使う。
  5. receipt_image_hash_registry にハッシュを予約する（table_name は NULL）。保存済みなら409。
  6. 別スレッドでモンスターカードの下書きを作る（計算式のみ、生成AIは使わない）。
  7. lines・sha256・structuredData を返す。DBのレシートテーブルは作らない。

3. 保存処理

  1. lines から null を除き、空なら400 EMPTY_RECEIPT。sha256 を検証して小文字にする。
  2. PersonalInfoSanitizer で構造化データと行を置換する。除去できなければ422。
  3. トランザクションの外で、生成AI（GEMINI_API_MONSTER → GEMINI_API_DEFAULT）でカードのパラメータとイラストを作る。失敗したら計算式・代替イラスト。
  4. トランザクション内で、予約済みハッシュに新しいテーブル名を設定（条件付きUPDATE。0件なら409）、receipt_＜32桁＞ テーブルを作って行を登録、構造化データを登録、カードを有効化（下書きがあれば上書き）する。
  5. tableName・lineCount・lines（置換後）・sha256 を返す。

4. 一覧・詳細・削除処理

  • 一覧：information_schema から receipt_ で始まるテーブルを名前の降順で取り、形式が正しいものだけ行数と最新の作成日時を集計する。
  • 詳細：形式と存在を確かめ、行番号順に返す。
  • 削除：トランザクション内で、レシートのテーブルを DROP し、receipt_structured_item・receipt_structured_summary・monster_card・receipt_image_hash_registry の該当行を削除する。

5. 認証処理

  • InMemoryUserDetailsManager に、ADMIN_USERNAME と ADMIN_PASSWORD_HASH（BCrypt）の1名をROLE_ADMINで登録する。
  • ログインは AuthController が AuthenticationManager で照合し、成功時にセッションIDを変更、SecurityContext をセッションへ保存、CSRFトークンを破棄する。
  • ログイン前に LoginAttemptLimiter で試行枠を確保し、照合結果を記録する。
  • フォームログイン・HTTP Basic は無効。ログアウトは /api/auth/logout（204）。

6. 対戦処理

  • ルームの操作は TransactionTemplate のトランザクション内で、monster_room を SELECT … FOR UPDATE してから行う。
  • 席トークンは256ビットの乱数（Base64URL）。DBにはSHA-256だけ保存する。
  • アクセスのたびに自分の最終アクセス時刻と有効期限（120分）を更新し、待機時間を過ぎていればコンピュータ対戦へ進める。
  • 両者が決定したら MonsterBattleEngine で計算し、結果を monster_battle に保存する。以後の GET …/battle はこの結果を返す。
  • コンピュータの手番は MonsterTaskRunner（2スレッド、待ち行列200）で行う。Geminiの呼び出し中は行ロックを持たない。
  • 画像カードは、状態確認 → （ロックなしで）Gemini読み取り・カード生成 → 再確認して登録、の3段階で行う。

7. 実装原則

  • 業務エラーは ReceiptException（HTTPステータス・コード・メッセージ）で投げ、ApiExceptionHandler が {code, message, timestamp} にする。想定外の例外は500 INTERNAL_ERROR とし、スタックトレースは応答に出さずログに残す。
  • テーブル名は ReceiptTableName.generate()（UUID由来）で作り、SQLに埋め込む前に必ず形式を検証する。値はすべてバインド変数で渡す。
  • テーブルはアプリが実行時に作成する（CREATE TABLE IF NOT EXISTS）。
  • 生成AIの応答は未検証の値として扱い、件数・長さ・範囲・許可リストに収める。
  • 設定値は application.yml に置き、秘密情報には既定値を書かない。
