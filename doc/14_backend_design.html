1. レイヤ構成

パッケージ（com.example.receipt）主なクラス責務
controllerAuthController、ReceiptController、HealthController、ApiExceptionHandler管理系API、例外のJSON変換
configSecurityConfig、DirectAccessRedirectFilter、GeminiApiKeys認可・CSRF・ヘッダー、直接アクセス転送、用途別キー
serviceReceiptService、GeminiReceiptAnalyzer、ReceiptUploadValidator、ImageInspector、LoginAttemptLimiter解析・保存の業務、画像検査、ログイン試行制限
repositoryReceiptTableRepository、ReceiptTableNameレシートごとのテーブル作成とSQL
dtoReceiptText、ReceiptSaveRequest、ReceiptStructuredData ほか入出力と入力検証
monsterMonsterController、MonsterRoomService、MonsterCardService、MonsterRateLimiter、GeminiMonsterAiルーム進行、カード連動、AI呼出し、回数制限
monster.engineMonsterCardGenerator、MonsterBattleEngine、PersonalInfoSanitizer、MonsterSvgValidator、MonsterSvgRendererDB・通信を持たない計算、個人情報の置換、SVG検証

2. 解析処理

  1. ReceiptUploadValidator で空・サイズ・種別・先頭バイト・画素数を検査する。
  2. SHA-256を計算し、GeminiReceiptAnalyzer で解析する（GEMINI_API_ANALYZE → GEMINI_API_DEFAULT）。
  3. 応答はJSONスキーマで受け取り、行の文字列と構造化データを正規化する。
  4. 画像ハッシュを予約する（保存済みなら409）。
  5. 応答後に別スレッドでカードの下書きを作る。解析ではレシート用テーブルを作らない。

3. 保存処理

  1. lines と sha256 を検証する。
  2. PersonalInfoSanitizer で個人情報を「（非表示）」に置換する。取り除けなければ422で保存しない。
  3. トランザクションの外でカードを準備する（Gemini呼出しは時間がかかるため）。
  4. トランザクション内で receipt_ テーブルの作成、行の挿入、構造化データの保存、カードの有効化をまとめてコミットする。

4. 一覧・詳細・削除処理

  • 一覧はテーブル名の降順。テーブル名は receipt_ + 32桁16進数の形式のみ受け付ける。
  • 削除はレシート、構造化データ、画像ハッシュ、カードを削除する。存在しなければ404。

5. 認証処理

  • 管理者は環境変数の ADMIN_USERNAME と ADMIN_PASSWORD_HASH（BCrypt）で1名を定義する。
  • ログイン成功でセッションIDを変更し、ログイン前のCSRFトークンを破棄する。
  • LoginAttemptLimiter が失敗回数をメモリで数え、5回でロックする。

6. 実装原則

  • 勝敗とカード生成はサーバーで計算する。
  • AIの出力は検証してから使い、失敗時は計算式へ切り替える。
  • SQLのテーブル名は固定パターンのみ許可する。
  • ログにAPIキー・画像本文・個人情報を出さない。
