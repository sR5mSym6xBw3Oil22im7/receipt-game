1. 目的

要件定義・設計どおりに、認可・入力検査・解析・保存・個人情報の除去・カード生成・対戦が動くことを、自動テストと手動確認で確かめる。

2. テスト範囲

区分対象方法
単体APIキー、入力検査、画像検査、ログイン試行制限、テーブル名、個人情報の除去、SVG検証、カード生成・対戦の計算、日時の解析JUnit
結合認証・認可・CSRF、解析・保存・一覧・詳細・削除、直接アクセスの転送、セキュリティヘッダー、対戦の流れ、回数制限Spring Boot Test（MockMvc、H2、Gemini は差し替え）
一致検査Java とデモの JavaScript のカード生成・対戦MonsterEngineParityTest（engine-parity.json）
フロントエンドHTML の要素・属性、スクリプトの内容、ファイルの一致、server.mjs の挙動node:test（smoke.test.mjs）
手動実際の Gemini・PostgreSQL・ブラウザーでの操作、公開環境「テスト仕様書」の手動確認

3. テスト環境

項目内容
バックエンドJava 21、Maven、H2（PostgreSQLは不要）
フロントエンドNode.js 22。リポジトリ直下で実行。server.mjs のテストはポート5051を使う
手動確認ローカル（Docker の PostgreSQL、reBack/.env の Gemini キー）と公開環境

4. 開始・終了条件

条件内容
開始ビルドが通る。テスト対象の変更がコミット前の状態でそろっている
終了自動テストがすべて成功する（環境起因の失敗は原因を記録し、環境を整えて再実行する）。手動確認の項目がすべて期待どおり
中断Gemini の上限・Render の停止など、外部要因で確認できない場合は、時間をおいて再開する

6. 不具合管理

  • 不具合は再現手順・期待・実際・原因・対応を記録し、修正と同じ変更でテストを追加する。
  • セキュリティの指摘は review/ に記録し、対応状況（修正済・一部修正・現状維持）を残す。
  • 環境起因（ポートの競合、外部サービスの停止）の失敗はコードの不具合と区別して記録する。
