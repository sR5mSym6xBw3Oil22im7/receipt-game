1. 作品概要

項目内容
作品名モンスターレシート対戦
ひとことでレシートが、そのままモンスターになって戦うWebゲーム
仕組み生成AI（Gemini）でレシートを読み取り、金額・品数・時刻・日付などからカードの能力を決める。2人がルームコードで集まり、サーバーが勝敗を計算する
公開先メニュー（GitHub Pages）、API・画面（Render）
構成Java 21 / Spring Boot 4.1.0、PostgreSQL、HTML / CSS / JavaScript（ビルド不要）

2. 担当範囲

企画、要件定義、画面・API・DBの設計、フロントエンドとバックエンドの実装、生成AIのプロンプトと応答スキーマ、テスト、Render・GitHub Pagesへの公開、セキュリティレビューへの対応、開発文書の作成までを一人で担当した。

3. 工夫点

観点内容
AIを信用しすぎない応答はJSONスキーマで形を決め、数値は範囲に収め、名前はカタカナ、SVGは許可リストで検証する。AIが使えなくても計算式と代替イラストで遊べる
個人情報保存前に正規表現で検出して置換し、取り除けなければ保存しない。正規表現はReDoSにならないよう線形時間にした
公正な対戦勝敗はサーバーでシード付き乱数を使って計算し、相手のカードは対戦開始まで返さない。画面は結果を再生するだけ
同じ計算を2か所でJava（本番）と JavaScript（デモ）で同じカード生成・対戦を実装し、テストで一致を確かめる
読み取りの精度回転したレシートは向きを推定して読み直す。年がかすれた日付は、印字された曜日から正しい年に直す
ログイン不要の安全な対戦席トークン（256ビット）をハッシュで保存し、IPごとの回数制限とGeminiの1日の上限を設けた
見た目の楽しさ10種類のテーマが毎日切り替わる。演出はCSSだけで、動きを減らす設定では止まる

4. 使用技術

  • Java 21、Spring Boot 4.1.0（Web / Security / Validation / JDBC）、JdbcTemplate
  • PostgreSQL、H2（テスト）
  • Google Gen AI SDK（google-genai 1.67.0）、Gemini（gemini-3.5-flash-lite）、Gson
  • HTML / CSS / JavaScript、DecompressionStream（ZIP展開）、SVG
  • JUnit 5、Spring Security Test、node:test
  • Docker、Render（Web Service・PostgreSQL）、GitHub Pages

5. 開発で得たこと

  • 生成AIを組み込むときは、プロンプトよりも「出力をどう検証し、失敗したらどうするか」の設計が重要だと分かった。
  • Spring Security の挙動（CSRF・認可・エラー応答）を、思い込みではなくテストで確かめる習慣がついた。
  • 同じロジックを2言語で持つ場合、期待値ファイルを共有して一致を検査すると安心して変更できる。
  • 無料枠の制約（起動の遅さ、メモリ上の状態）を前提に、機能の範囲を決める判断ができた。

6. 課題と改善案

課題改善案
ポーリングによる状態確認WebSocket や Server-Sent Events で通知する
メモリ上の回数制限・ログイン試行DB や Redis に移し、再起動・複数台でも維持する
個人情報の検出漏れ（市区町村だけの住所など）規則を増やす、または生成AIによる二重確認を加える
偽造レシートで強いカードを作れる能力値の上限を調整する、画像カードの能力に制限を設ける
対戦の記録が残らないルームとは別に、匿名の戦績を保存する
