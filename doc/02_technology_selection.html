1. 選定方針

  • 公開・運用の費用を抑えるため、無料枠で動かせる構成（GitHub Pages、RenderのFreeプラン）にする。
  • フロントエンドはビルド不要の静的ファイルにし、変更をそのまま配信できるようにする。
  • 認証・認可・CSRFは自作せず、実績のあるSpring Securityに任せる。
  • 生成AIの応答はJSONスキーマで形を固定し、受け取った値はサーバーで検証してから使う。
  • 対戦の勝敗はサーバーで計算する。乱数はシード付きにして、同じ入力から同じ結果を再現できるようにする（デモのJavaScriptと同じ計算を行う）。

2. 採用技術

分類技術版用途・採用理由
言語（バックエンド）Java21record・switch式・Math.clamp など新しい言語機能で記述量を減らす。
フレームワークSpring Boot（Web / Security / Validation / JDBC）4.1.0REST API、セッション認証、CSRF、Bean Validation、静的ファイル配信をまとめて扱える。
DBアクセスJdbcTemplateSpring Boot 付属レシートごとにテーブルを作るため、ORMではなくSQLを直接扱う。
データベースPostgreSQL本番18（Render）、ローカル16（Docker）トランザクションと行ロック（SELECT … FOR UPDATE）でルームの操作を順番に処理する。
テスト用DBH2（PostgreSQL互換モード）Spring Boot 管理PostgreSQLなしで mvn test を実行できる。
生成AIGoogle Gen AI SDK（com.google.genai:google-genai）1.67.0Geminiへ画像・プロンプトを送り、JSONスキーマ指定の応答を受け取る。
JSONGson2.13.1Geminiの応答や、ルームのプレイ状態（JSON文字列の列）の変換。
フロントエンドHTML / CSS / JavaScript—ビルド不要。ZIPの展開はブラウザー標準の DecompressionStream を使う。
ローカル配信Node.js（server.mjs）22で確認reFront/ を http://localhost:5051 で配信する。テストにも使う。
テストJUnit 5、Spring Boot Test、Spring Security Test、node:test—API・認可・計算処理の自動テストと、HTML・スクリプトの内容検査。
コンテナDocker（maven:3.9.11-eclipse-temurin-21-alpine → eclipse-temurin:21-jre-alpine）—Renderでのビルドと実行。
ホスティングGitHub Pages / Render（Web Service・PostgreSQL）Freeフロントエンドと、API・DBをそれぞれ無料枠で公開する。

3. 不採用・保留技術

技術判断理由
React などのSPAフレームワーク不採用画面数が少なく、ビルド工程を持ち込む利点が小さい。
JPA / Hibernate不採用レシートごとに動的にテーブルを作る設計と合わない。
WebSocket保留対戦の進行はポーリング（1〜2秒間隔）で足りる。Freeプランでの接続維持の不安もある。
利用者アカウント（会員登録）不採用対戦はルームコードと席トークンだけで成り立つ。個人情報を持たないほうが安全。
画像の保存（オブジェクトストレージ）不採用個人情報を含みうる画像を保持しない。重複判定はSHA-256で行う。
ウイルス対策エンジン保留サーバーで画像をデコード・再配信しないため優先度を下げた。先頭バイトと画素数の検査だけ行う（残存リスクとして記録）。

4. 技術上の制約

  • RenderのFreeプランは、しばらくアクセスがないと停止し、次のアクセスで起動に時間がかかる。
  • Gemini APIには利用上限がある。上限に達した場合は429として扱い、用途別のキーと既定のキーを順に試す。カード生成は計算式の値と代替イラストで続行する。
  • ログイン試行の記録と、対戦APIの回数制限は、アプリのメモリ上にだけ持つ。再起動で消え、複数インスタンスでは共有されない。
  • GitHub Pagesからバックエンドへは別オリジンになるため、管理画面・対戦画面はバックエンドから配信し、APIは同一オリジンで呼び出す。
  • ZIPの展開はブラウザーの DecompressionStream に依存する（未対応のブラウザーではZIPを解析できない）。
